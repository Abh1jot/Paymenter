# Security & Architecture Policy

This document outlines the security architecture, threat model, and defense-in-depth principles implemented in the **Pterodactyl v2 Extension for Paymenter**.

---

## 1. Threat Model & Security Controls

Hosting control integrations operate in high-risk multi-tenant environments. A vulnerability in server resolution, power management, or lifecycle handling could lead to cross-customer server hijacking, unauthorized data destruction, or credential leaks.

The following security controls are strictly enforced:

### A. Multi-Tenant Customer Ownership Verification
- Every customer-facing action (viewing status, triggering power actions, revealing or rotating credentials) routes through `Livewire/ServerManager.php`.
- Before executing any logic, the component verifies:
  ```php
  if ($this->service->user_id !== auth()->id() && !auth()->user()?->can('admin')) {
      abort(403, 'Unauthorized access to server controls.');
  }
  ```
- **No Client-Supplied Identifiers**: The client browser never supplies the Pterodactyl server ID or UUID. The identifier is looked up server-side directly from the authenticated `Service` model.

### B. Safe Destruction & Cross-Customer Termination Guards
- Server termination (`terminateServer`) will **never** execute an API deletion call without first querying Pterodactyl to confirm the server's identity.
- In `Services/LifecycleService.php`, the server's `external_id` is retrieved from the Pterodactyl API and verified against the Paymenter `$service->id`:
  ```php
  if (!empty($server->externalId) && (string) $server->externalId !== (string) $service->id) {
      throw new Exception("Security violation: Server external_id mismatch. Deletion blocked.");
  }
  ```
- This guarantees that an incorrect database mapping or rogue configuration can never cause the deletion of another customer's server.

### C. Automatic API Token Redaction
- Application tokens (`ptla_...`) and Client tokens (`ptlc_...`) possess administrative permissions and must never appear in logs or error traces.
- `Services/PterodactylClient.php` runs all outbound exception messages and logs through a secret scrubbing engine:
  ```php
  $redacted = preg_replace('/(ptla_[a-zA-Z0-9_-]{10})[a-zA-Z0-9_-]+/', '$1***REDACTED***', $message);
  $redacted = preg_replace('/(ptlc_[a-zA-Z0-9_-]{10})[a-zA-Z0-9_-]+/', '$1***REDACTED***', $redacted);
  ```
- Application logs will never store unredacted Pterodactyl API tokens.

### D. Strict TLS Certificate Verification
- Outbound API requests use Laravel's `Http` client with strict TLS certificate verification enabled by default.
- TLS verification is never disabled or bypassed via curl flags. Self-signed certificates must be added to the operating system's trust store rather than disabling transport security.

### E. Idempotent Provisioning Guard
- Network timeouts during server creation can lead to duplicate containers being created if the administrator or customer retries the operation.
- `Services/ProvisioningService.php` checks whether a server with `external_id = (string) $service->id` already exists on the panel before submitting a `POST /api/application/servers` request.
- If an existing server is found, the extension reconciles and associates the existing server without spawning duplicate billing or hosting overhead.

### F. Cryptographic Password Generation & Storage
- Passwords generated by `Services/PasswordService.php` use `random_int()` over a 72-character alphabet (mixed-case alphanumeric and symbols) to guarantee high entropy (16 characters minimum).
- Passwords stored in `service_properties` are encrypted at rest using Laravel's `Crypt::encryptString()` (AES-256-CBC cipher authenticated with HMAC-SHA256).

## 2. API Scope & Minimum Permissions Checklist

To adhere to the principle of least privilege, configure your Pterodactyl API keys with only the required permissions:

| Resource | Application Key (`ptla_`) | Client Key (`ptlc_`) |
| :--- | :---: | :---: |
| **Servers** | Read & Write | Read, Power Actions |
| **Users** | Read & Write | None |
| **Nodes** | Read & Write | None |
| **Allocations** | Read & Write | None |
| **Nests / Eggs** | Read | None |
| **Databases** | Read & Write (Optional) | None |

---

## 3. Reporting a Security Vulnerability

If you discover a potential security flaw in this extension:
1. Do not open a public issue on community forums or marketplaces.
2. Contact the security team directly with reproduction steps and proof-of-concept details.
3. Security patches are prioritized and released promptly.
